# 11 FPGA 加速平台与硬件配置方案

> 目标：**FPGA 单卡（可扩展多卡）加速运行 DeepSeek-V4-Flash**，作为 vdot 大赛作品的最终落地演示平台。
> 模型规格（官方，2026-04-24 发布）：DeepSeek-V4-Flash = **总参 284B / 激活参 13B / 上下文 1M**，DeepSeekMoE + 混合注意力（Compress-4/128-Attention）+ KV 滑窗压缩。
> 性能目标：**≥50 token/s（解码吞吐）**；平台：**AMD/Xilinx Alveo/Versal**；架构要求：**单卡主交付 + 多卡可扩展**。

---

## 1. 目标与定位

| 项 | 决策 |
| --- | --- |
| 主交付 | **单卡**运行"V4-Flash 同架构小型化模型"（DeepSeekMoE+混合注意力同构，~20B 总参/2B 激活，INT8），≥50 token/s |
| 扩展交付 | **多卡（4–8 张）**运行**全量 284B**：4×32GB 卡 INT2（71GB 权重）或 8×32GB 卡 INT4（142GB 权重），目标 20–80 token/s |
| 与大赛作品关系 | FPGA 平台是 vdot 指令（02/03 设计）的**系统级验证与演示载体**：vdot 单元在 PL 中实现并作为 GEMM 加速原语，香山核做控制/调度/专家路由 |
| 为什么可行 | MoE 每 token 计算量由**激活参 13B** 决定（~26 GMAC/token），算力上单张 Versal 级卡即可支撑 ≥50 token/s；瓶颈是**容量与带宽**，由"小型化入卡 + 多卡扩展"两级方案解决 |

### 1.1 可行性结论（先算账）

| 约束 | 全量 284B | 结论 |
| --- | --- | --- |
| 容量 | INT8=284GB / INT4=142GB / INT2=71GB | 单卡（≤32GB HBM2e）**装不下全量**；INT2 需 ≥4 卡、INT4 需 ≥8 卡 |
| 算力 | 26 GMAC/token；50 token/s = 1.3 TMAC/s | 1 张 Versal PL 即接近满足（~1.4 TMAC/s INT8）→ **算力不是瓶颈** |
| 带宽 | INT4 激活权重 @50 t/s = 325GB/s（摊到 8 卡 = 40GB/s/卡） | 8 卡 HBM 819GB/s/卡，**带宽有余量** |

> 因此本方案分两级：**单卡跑同构小型化模型（可入卡、性能好、架构同构可扩展）** + **多卡跑全量（容量分摊、带宽分摊）**。

## 2. 需求建模（公式与核算）

### 2.1 三个关键公式

```
① 权重容量  W = N_total × bits / 8          （必须 ≤ 板载内存 - KV - 激活余量）
② 每 token 计算  C ≈ 2 × N_active × bits/8 的 MAC 数 → 2×N_active MAC（decode，KV 复用）
   解码吞吐上限（compute-bound）= 板卡 INT8 MAC 峰值 / C
③ 每 token 权重带宽  B = N_active × bits/8 字节（MoE 动态路由，每 token 读激活专家权重）
   解码吞吐上限（bandwidth-bound）= 板卡内存带宽 / B
```

### 2.2 核算表（本方案取值）

| 场景 | 总参/激活 | 量化 | 权重容量 | 每 token MAC | @50 t/s 算力 | @50 t/s 带宽 | 是否入单卡 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 全量 V4-Flash | 284B/13B | INT4 | 142GB | 26 GMAC | 1.30 TMAC/s | 325 GB/s | ✗（需 8 卡） |
| 全量 V4-Flash | 284B/13B | INT2 | 71GB | 26 GMAC | 1.30 TMAC/s | 162 GB/s | ✗（需 4 卡） |
| **小型化同构（主交付）** | 20B/2B | INT8 | **20GB** | 4 GMAC | 0.20 TMAC/s | 100 GB/s | **✓（32GB 卡）** |
| 小型化同构（备选） | 30B/3B | INT4 | 15GB | 6 GMAC | 0.30 TMAC/s | 75 GB/s | ✓（16GB 卡也可） |

> KV Cache：1M 上下文经 V4 的滑窗压缩后仍达数 GB~数十 GB 级，单卡演示取 32K–128K 上下文（压缩后 ~1–4GB），多卡全量按序列并行分摊；INT8 激活 + KV 压缩量化进一步降低。

## 3. 单卡方案（主交付，≥50 token/s）

### 3.1 卡型选型（AMD/Xilinx）

| 卡型 | 板载内存 | 带宽 | 算力资源 | 适用 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **Versal HBM VHK158**（推荐） | 32GB HBM2e | ~819 GB/s | PL DSP ~4K + 逻辑，PCIe Gen4 x16 | 20B/2B INT8 入卡有余量 | **★ 主选** |
| Versal AI Core VCK5000 | 32GB HBM2e | ~819 GB/s | PL DSP ~4K + **400 AI Engine 核** | 同 VHK158，AIE 可做备用加速 | 备选（AIE 编程成本高，非 vdot 路径） |
| Alveo U55C | 16GB HBM2e | ~460 GB/s | DSP ~4.5K | 30B/3B INT4（15GB）或 KV 压缩后的小型化 INT8 | 预算降档 |
| Alveo U280 | 8GB HBM2 + 64GB DDR4 | HBM 460 GB/s | DSP ~4K | 权重放 HBM、溢出放 DDR4 | 不推荐（HBM 偏小） |
| Alveo U250（无 HBM） | 64GB DDR4 | ~77 GB/s | DSP ~4K | — | **✗ 带宽不足**（<100GB/s 需求） |

> 以上为典型值，以厂商数据表为准。**推荐：1× Versal VHK158（或 VCK5000）**。

> 💡 **云上等价目标（2026-08 更新）**：**AWS F2** 实例使用 **AMD Virtex UltraScale+ HBM VU47P**（16GB HBM2e + 64GB DDR4/FPGA），f2.6xlarge 单 FPGA、f2.12xlarge 双 FPGA、f2.48xlarge 8 FPGA（128GB HBM + 512GB DDR4）——**云上即可覆盖单卡主交付与全量 284B 多卡场景**，按小时计费（详见 [12 §5.1](./12_硬件市场价格与启动投资估算.md)）。建议将 **F2（VU47P）与 VHK158（Versal HBM）并列为目标平台**：RTL 同源、按平台分别综合收敛；优先用 F2 云资源开发与演示，实体卡作为长期自用/离线选项。

### 3.2 片上计算架构（两级算力）

```
┌────────────────────────── Versal HBM VHK158（单卡）──────────────────────────┐
│  PS（ARM 处理器系统）                                                        │
│    └─ host 侧：驱动/推理栈（vLLM 子集或自研 runtime）、量化、调度             │
│  PL（可编程逻辑）                                                            │
│    ├─ ① 香山核（MinimalConfig 子集，~50–100MHz）                             │
│    │    · 跑 vdot 指令集：控制平面、专家路由（top-k 选择）、KV 压缩、         │
│    │      反量化/打包胶水代码（04 的 kernel）                                 │
│    ├─ ② INT8 点积加速阵列（主算力）                                          │
│    │    · 以 vdot 数据视图（32-bit = 4×INT8 打包）为统一原语                  │
│    │    · 可配置乘加簇/小型脉动阵列，规模按目标 token/s 裁剪                  │
│    │    · ~0.2 TMAC/s 即可满足 50 token/s（20B/2B），PL 富余量用于预留扩展    │
│    ├─ ③ 权重/激活缓存：BRAM/URAM 分块 + HBM 流式                            │
│    └─ ④ PCIe Gen4 x16 DMA（QDMA/XDMA）                                      │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **vdot 与阵列的关系**：香山核的 vdot 指令（02/03 设计）提供"4×INT8→INT32 点积累加"的指令级原语；GEMM 加速阵列采用**相同数据视图**（权重打包布局一致，见 04 §4.3），两者共用同一量化/打包格式——核内 vdot 跑小矩阵/控制流/路由，阵列跑大 GEMM，指令语义与硬件原语完全同构，避免两套格式。
- **香山核在 FPGA 的现实约束**：昆明湖全核在 FPGA 上面积/时序困难（目标 1.5GHz，FPGA 一般 ≤100–200MHz）。方案：用 MinimalConfig 子集核降频运行，仅承担控制/调度/路由（不承担主算力）；主算力由②阵列承担。若连子集核也吃紧，备选：用香山核的**vdot 数据通路**直接作为协处理器挂到轻量 RISC-V 控制核（在 06 计划中作为决策点）。
- **AI Engine 备选**：VCK5000 的 AI Engine 阵列可提供数十~上百 TOPS INT8，但编程模型与 vdot 指令路径不同；作为"性能极限演示"备选，不作为主路径。

### 3.3 存储与数据流

```
权重（静态，INT8 打包 4×8bit/32bit）─► HBM 权重区（~20GB）
                                          │ 按专家分块（DeepSeekMoE：每层 64 experts）
                                          ▼
路由（香山核）─► 每 token 选 top-k 专家 ─► 流式读激活专家权重（~2GB/token）─► 阵列
                                          ▼
                                KV Cache（滑窗压缩 + INT8）~1–4GB @32K–128K ctx
```

- 量化：INT8 W8A8（对称，per-group scale），与 vdot 累加路径一致（02 §4.3 回绕累加 → 反量化移出 K 循环）。
- 打包：权重离线打包（04 §4.3），专家粒度分块，方便路由按需加载。

### 3.4 性能预估（单卡主交付）

| 项 | 值 | 依据 |
| --- | --- | --- |
| 模型 | 20B 总参/2B 激活 MoE，INT8，32K ctx | 同构缩放 |
| 算力需求 | 0.2 TMAC/s | 4 GMAC/token × 50 |
| 带宽需求 | 100 GB/s | 2GB/token × 50 |
| VHK158 能力 | 算力 ~1.4 TMAC/s（PL INT8），带宽 819 GB/s | 算力利用率 ~14%，带宽 ~12% |
| **预估解码吞吐** | **50–100+ token/s** | compute/bandwidth 均富余，实际受路由/调度开销限制 |

## 4. 多卡方案（扩展，全量 284B）

> 回答"一台机器多卡是否支持"：**支持**。多卡通过 PCIe Gen4 互联（host 中介或 P2P），以**专家并行（EP）为主**分摊容量与带宽；架构与单卡完全同构（每卡 = 香山核 + 阵列 + 权重分片）。

### 4.1 并行策略

| 并行度 | 对象 | 说明 |
| --- | --- | --- |
| **EP（专家并行，主）** | MoE 专家按卡分片（284B 权重均分） | 每 token 由路由选择专家 → 跨卡收集（all-to-all）；每卡只存自己的专家分片 |
| TP（张量并行） | 注意力/共享层按列分片 | 对激活小、权重大的注意力部分收益高 |
| 序列并行 | 长上下文（1M）KV 按序列段分卡 | 配合 V4 滑窗压缩，KV 按窗口分片 |
| MTP/投机解码（可选） | 模型自带 MTP 头 | 提升有效吞吐（软件层） |

### 4.2 互联与通信

- 物理：每卡 PCIe Gen4 x16（~32GB/s 单向），支持 P2P 时专家 all-to-all 走卡间直连，否则 host 中介。
- 通信量：每 token 每层交换"路由结果 + 隐层张量"（专家并行典型模式），量级为每 token 每卡数十 MB → 50 token/s 时 ~1–3 GB/s/卡，**PCIe 带宽足够**（通信不是硬瓶颈，但延迟/同步开销需软件优化，如多 token 批处理掩盖）。
- 拓扑：4/8 卡星型接 host（AMD 无 NVLink 等价物），软件层以批量路由降低 all-to-all 频率。

### 4.3 全量 284B 配置

| 配置 | 卡数 | 量化 | 权重占用 | 剩余（KV/激活） | 预估吞吐 |
| --- | --- | --- | --- | --- | --- |
| **推荐（INT4 质量优先）** | 8× VHK158（256GB） | INT4 | 142GB | ~114GB（1M ctx KV 压缩后富余） | 40–80 token/s |
| 经济（INT2 容量优先） | 4× VHK158（128GB） | INT2 | 71GB | ~57GB | 20–50 token/s |

- 每卡算力：26 GMAC/token × 50 = 1.3 TMAC/s ÷ 8 卡 = 163 GMAC/s/卡（VHK158 PL ~1.4 TMAC/s，**富余**）。
- 每卡带宽：INT4 激活权重 @50 t/s = 40GB/s/卡（819GB/s，**富余**）。
- 瓶颈：**EP all-to-all 路由效率与 KV 压缩后注意力访存**，实测以 vLLM 风格 runtime 的 EP 实现为准。

### 4.4 单卡 vs 多卡决策

| | 单卡（主交付） | 多卡（扩展） |
| --- | --- | --- |
| 模型 | 20B/2B 同构小型化，INT8 | 全量 284B，INT2/INT4 |
| 成本 | 1 卡（~$10–20K 级） | 4–8 卡 + 主机（数倍） |
| 吞吐 | 50–100+ token/s | 20–80 token/s |
| 风险 | 低（容量/带宽富余） | 中（EP 路由、KV 1M、框架适配） |
| 定位 | 大赛主演示、可复现 | 挑战性加分项 |

```
        ▼

```

## 7. 风险与备选

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 香山全核在 FPGA 时序/面积不达标 | 核跑不起来 | MinimalConfig 子集 + 降频（50–100MHz）；备选：vdot 数据通路作协处理器 + 轻量 RISC-V 控制核 |
| INT2/INT4 量化质量不满足任务精度 | 全量方案效果差 | 主交付用 INT8 小型化（质量无损路线）；全量方案标注"量化质量以实测为准" |
| EP all-to-all 通信开销导致吞吐低于预估 | 多卡性能不达标 | 批量路由掩盖延迟；单卡主交付不受影响 |
| 32GB 卡单卡 KV/权重余量紧张（1M ctx） | 上下文受限 | 主交付用 32K–128K ctx；1M ctx 走多卡序列并行 |
| AI Engine 与 vdot 路径不一致 | 想用 AIE 加速 | 明确 AIE 为备选，主路径为 PL DSP + vdot 原语 |
| 工具链（Vitis/HLS 或 RTL 流程）学习成本 | 进度风险 | 复用 04 的 kernel 与打包器；FPGA 流程与 RTL 并行推进，不阻塞阶段一~三 |
